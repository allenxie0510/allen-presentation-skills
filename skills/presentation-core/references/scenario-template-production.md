# Scenario template production method

Use this method to create or substantially upgrade a presentation template for a
new scenario or industry. It converts a successful one-off deck into a reusable
system without forcing later templates to share its visual style.

## Separate invariants from expression

Every template inherits the release invariants: truthful evidence, editable
output, room-scale typography, slot-aware imagery, source notes, varied cadence,
accessibility, and render-based QA.

Every template must redesign the expression variables from its own brief:

- narrative tension and audience decision;
- industry evidence and work artifacts;
- cultural context, cast, workplace, clothing, and photographic language;
- composition, typography character, color behavior, component grammar, and
  rhythm;
- interaction, practice, assessment, or decision moments.

Do not treat Learning Agent, Signal Grid, or an example PPTX as a universal
visual skin. Reuse the method and constraints, not the page-specific look.

## Production stages

### 1. Normalize the brief and evidence

Record audience, presenter, setting, length, required belief or action, evidence
status, real assets, brand constraints, accessibility needs, and delivery format.
Separate verified facts, concept content, placeholders, and missing inputs before
any visual work.

### 2. Extract principles from references

Translate reference images into observable rules for hierarchy, density, spacing,
photography, color, typography, composition, and pacing. Record what must not be
copied: brand marks, original images, signature compositions, claims, and UI.

### 3. Resolve the design direction

If the visual premise is new or unresolved, use Allen FRAME: render the same
representative content through three structurally distinct directions, select or
mix one with recorded human input, then write the art-direction contract. Skip
this loop when an approved template already supplies the visual direction.

### 4. Build the narrative and slot inventory

Define one job and claim per slide. Assign every slide an archetype, energy,
silhouette, density, and evidence slot. Record the exact aspect ratio, safe zone,
fit, crop, focal point, provenance, disclosure, and semantic role for every image.

### 5. Author the image system

For recurring documentary imagery, define a cast-and-place bible before
generation: identities, role agency, workplace, clothing families, materials,
light, camera language, and continuity boundaries. Define the meaningful work
artifacts and allowed short labels for each scene. Generate for the destination
slot ratio; reject blank notes, unrelated diagrams, gibberish, fake UI, and
tokenistic diversity.

### 6. Prove representative frames

Before the full template, render at least the cover, narrative/evidence frame,
data or structure frame, activity or decision frame, and closing frame. Stress
the densest copy, smallest image slot, longest title, and most complex artifact.
Repair the system rather than adding page-specific exceptions.

### 7. Produce the native deliverable

Preserve a supplied template's master → layout → slide hierarchy. Keep text,
shapes, tables, charts, and notes editable. Replace inherited media in place when
editing an existing deck. For a new system, encode repeated layouts and image
slots as named rules instead of ad hoc coordinates.

### 8. Run release QA

Render every slide, inspect every slide full size, inspect a contact sheet, run
programmatic bounds/overflow checks, verify font substitution, sources, notes,
editable structure, crop integrity, complete in-image labels, cast continuity,
and the absence of meaningless artifacts. Re-render after the final change.

### 9. Promote and package

An agent may mark a profile `candidate`; only recorded human approval may promote
it to `approved`. A final scenario-template release should contain:

- a concise `SKILL.md` route and scenario-specific reference;
- schema-valid production profile;
- editable reference deck and contact sheet;
- image assets, prompt/cast record, and source/disclosure register;
- design review and a realistic regression eval;
- validation result and public-package build check when the Skill is public.

## Adoption rule for other scenario Skills

Keep this file as the canonical cross-scenario method. A portable scenario Skill
must include a self-contained, scenario-specific execution reference that applies
the method to its own evidence, narrative, components, and image language. Do not
link to an external local path or assume another Skill is installed.
